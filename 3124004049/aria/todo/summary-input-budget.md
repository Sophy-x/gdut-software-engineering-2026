# 指令：修复摘要输入预算过低导致压缩常态丢前半段历史

## 背景

- 现状：`_summary_input_budget`（`src/core/context.py`）= `message_budget // 2` ≈ 40k。
- 问题：触发压缩时总量约 84k，保留 `keep_recent_tokens` 20k 后，被压部分起步就是 64k+——天然是摘要预算的近两倍。`_limit_summary_source` 在**主路径**上常态砍掉被压历史的前半段，只送最近段并在开头声明省略。
- 实证：会话 `02e6e126` 的真实压缩（tokens_before=84,672，被压 85 条），摘要输入被截，模型在摘要里如实写下"原始任务描述被省略、无法从当前历史恢复"。
- 横向对比（pi / codex / dsh / minimax-code / oh-my-pi）：无一家使用"远小于主请求的摘要预算"。
  - pi / codex / dsh：不设摘要输入上限，全量送。pi 靠 reserve 提前触发兜底；codex 服务端报超窗后逐条删最老 item 重试；dsh 全量重放以复用前缀缓存，摘要不比被压内容小则整体失败。
  - oh-my-pi：`floor(0.8 × 窗口) − 输出预算 − 16k`（200k 窗口 ≈ 128k），超出时折叠多窗口迭代摘要。注释明说用 0.8 而非"窗口 − reserve"是给估算误差留余量：估错一次就是硬 400，而这恰是拯救超限会话的那次调用。
  - minimax-code：上限 = 主请求的 providerInputLimit（窗口 95% − 输出预留），超出走五级候选阶梯（结构性删除，不截摘要文本）。

## 改动 1：摘要输入预算提到接近主请求

- `_summary_input_budget`：`message_budget // 2` → `floor(0.85 × context_window) − 摘要输出预留`。
- 理由：正常压缩被压部分 ≈ 64k~80k，改后全量送入；留 ~15% 吸收字符估算对源码类文本的低估（omp 同款理由）。
- 摘要请求不带工具定义（`stream_chat` 无 tools 参数），可用空间比主请求更宽，0.85 系数安全。

## 改动 2：超出时的降级从"丢弃"改"折叠"

- 现状：`_limit_summary_source` 只送最近段 + 声明省略（丢前半段）。
- 改为 omp 式折叠：按消息边界切成多个 ≤ 预算的窗口，逐窗口调用摘要，后一窗的输入携带前一窗产出的 summary 迭代更新（可参考现有累计摘要 `_summary_source` 的拼法），最终 summary = 最后一窗输出。
- 服务端报 context_overflow 时对半缩小窗口重试，下限 16k。
- 省略声明只保留给"单条消息本身超预算"的场景（对应 omp 的 clampConversationToBudget）。

## 观察项（不实施，记录）

- dsh 摘要时原样重放消息序列（system + 被压区间），不序列化成纯文本，以复用主请求的前缀 KV 缓存；我们 `_serialize_messages` 转纯文本，摘要请求永远全价。若未来摘要请求量变大，再评估重构消息构造。

## 验收标准

1. 单测：被压部分 ≤ 新预算时，摘要输入全量放行，不插省略提示。
2. 单测：被压部分 > 新预算时走折叠路径，最终摘要由全部窗口内容汇成。
3. 单测：折叠中单窗 overflow → 窗口减半重试，下限 16k 生效。
4. 真实多轮会话验证一次：压缩触发后摘要不再出现"原始任务描述被省略"。
5. 完整测试集通过。

## 约束

- 不改 `CompactionRecord` 持久化结构。
- 折叠只在超出预算时启用，正常路径仍是单次摘要请求（不增加常规成本）。
- 先做改动 1 并跑测试，再做改动 2。
